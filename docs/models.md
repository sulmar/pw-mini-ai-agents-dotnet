# Modele LLM

W ramach zajęć i projektu można korzystać zarówno z modeli LLM uruchamianych lokalnie, jak i modeli udostępnianych poprzez API.

Wybór modelu jest częścią projektu. Zespół powinien dobrać model odpowiedni do wymagań swojego rozwiązania.

Korzystanie z płatnych modeli i usług nie jest wymagane.

## 1. Modele lokalne

Modele lokalne mogą być uruchamiane bezpośrednio na komputerze studenta, bez konieczności korzystania z zewnętrznego API.

Podczas zajęć do uruchamiania modeli lokalnych rekomendowane jest:

**Ollama**  
https://ollama.com

Ollama umożliwia pobieranie i uruchamianie różnych modeli LLM oraz korzystanie z nich z poziomu aplikacji.

Przy wyborze modelu lokalnego należy uwzględnić między innymi:

- wymagania sprzętowe,
- wielkość modelu,
- szybkość działania,
- dostępny kontekst,
- obsługę tool calling,
- możliwości modelu wymagane przez projekt.

Lista rekomendowanych modeli może być aktualizowana w trakcie semestru.

## 2. Modele przez API

Alternatywą dla modeli lokalnych jest korzystanie z modeli LLM udostępnianych poprzez API.

### PLGrid / PCSS

W ramach zajęć można wykorzystać infrastrukturę udostępniającą modele LLM poprzez API.

**PLCloud**  
https://pcss.plcloud.pl/

**Lista dostępnych modeli LLM oraz dostęp do API**  
https://llm.hpc.psnc.pl

Dostępność konkretnych modeli może zmieniać się w trakcie semestru. Przed rozpoczęciem implementacji należy sprawdzić aktualną listę modeli oraz zasady dostępu do usługi.

## 3. Modele opcjonalne i płatne

Studenci mogą korzystać również z innych dostawców i modeli LLM, w tym usług komercyjnych.

Korzystanie z płatnych modeli lub płatnego API:

- jest opcjonalne,
- nie jest wymagane do realizacji projektu,
- nie wpływa samo w sobie na ocenę projektu.

Zespół samodzielnie odpowiada za ewentualne koszty związane z wykorzystaniem wybranej usługi.

## 4. Wybór modelu

Nie ma jednego modelu wymaganego dla wszystkich projektów.

Zespół powinien potrafić uzasadnić wybór modelu w kontekście swojego rozwiązania.

Przy wyborze warto uwzględnić między innymi:

- jakość generowanych odpowiedzi,
- obsługę tool calling,
- wielkość okna kontekstowego,
- szybkość działania,
- możliwość uruchomienia lokalnego,
- dostępność poprzez API,
- ograniczenia sprzętowe,
- limity i ewentualne koszty.

W trakcie realizacji projektu model może zostać zmieniony, jeżeli zespół uzna, że inny model lepiej odpowiada wymaganiom rozwiązania.
